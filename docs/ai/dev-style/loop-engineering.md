# Loop Engineering

## なぜ存在するか

AI エージェントを使った開発は、当初「人間がプロンプトを書く → エージェントが応答する → 人間が次のプロンプトを書く」という手作業の繰り返しだった。この形では、開発者が常にツールを握り続ける必要があり、スケールしない。

Loop Engineering は、エージェントに毎回指示を出すのではなく、**エージェントに指示を出す仕組み（ループ）そのものを設計する**アプローチ。開発者の役割は「プロンプトを書く人」から「ループを設計する人」へ移る。

:::info[発想の転換]
「エージェントをプロンプトする」のではなく「エージェントにプロンプトを出すループを設計する」。
:::

## 5つの構成要素

| 要素 | 役割 |
|---|---|
| **自動化（Automations）** | スケジュール実行によりタスクの発見・分類を自動で行う |
| **ワークツリー（Worktrees）** | 複数エージェントが並行作業する際の競合を防止する |
| **スキル（Skills）** | プロジェクト固有の知識を再利用可能な形で記述する |
| **コネクタ（Plugins/Connectors）** | Slack・Linear など既存ツールと統合する |
| **サブエージェント** | 作成者と検証者の役割を分離し、品質を高める |

これらに加えて、Markdown や Linear などによる**状態管理**がループの背骨になる。セッションをまたいで記憶を保持することで、ループが継続的に機能する。

## 典型的な活用シーン

毎朝のスケジュール実行により、以下が無人で進行する。

```
CI失敗を分析 → 課題を分類 → 修正案を作成・レビュー → PRを自動で開く
```

## リスク

ループの自動化は前進をもたらす一方、以下のリスクを伴う。

- **検証責任の所在**: 最終的な検証責任は依然として人間にある
- **理解の劣化**: ループに任せきることでコードの把握が薄れる
- **認知の放棄**: 考えることを避けるためにループを使うと、思考停止につながる

:::tip[設計者であり続ける]
ループを設計することは、判断力を持って行えば前進だが、思考を避けるためなら単なる加速ペダルになる。
:::

## いつ使うか

- 定型的なタスク（課題分類・修正提案・PR作成など）を繰り返し人間が指示している
- 複数のエージェントを並行して動かし、成果物をレビューする体制を作りたい
- セッションをまたいでプロジェクトの状態を保持しながらタスクを進めたい
